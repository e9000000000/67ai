# 67ai

A local Rust server and compact dark Kanban board for Codex. No Node build, hosted service, or API key is needed: it uses your installed Codex CLI and existing login.

## Run on Windows

Download `67ai.exe` from [GitHub Releases](https://github.com/e9000000000/67ai/releases), run it from a writable folder. It runs in the Windows notification tray without a console window. Right-click its icon and choose **Open in browser** to open the board, or **Exit** to stop the server and active runs. No browser tab opens automatically. Install Codex CLI and log in first. The downloaded executable does not require Rust; its UI is embedded. Data is saved in the working directory's `data` folder unless `67AI_DATA_DIR` is set.

### Build from source

Install Rust and Codex CLI, then run `codex login` if needed. From this folder:

```powershell
.\start.ps1
```

Open http://127.0.0.1:3030. The launcher builds the single release executable and starts it in the tray. Use the tray menu to open the board or exit. Debug builds retain the console and Ctrl+C shutdown. For development, use `cargo run`. The HTML, CSS and JavaScript are embedded in the executable, so rebuild after editing them.

After changes, run `.\restart.ps1` to stop this checkout's existing server, rebuild the release version, start it in the background, and open your default browser when it is ready. This interrupts any running task; interrupted tasks return to Future. The script respects `67AI_PORT` and `67AI_DATA_DIR`.

## GitHub releases

All development uses `main`, the repository's only branch, which tracks `origin/main`. Push with `git push`. The Windows release workflow runs on every push to `main` (not tag pushes), tests the code, builds the Windows x64 executable, and creates a GitHub release with `67ai.exe` attached. Each run gets a unique `windows-<run number>-<attempt>` tag targeting the pushed commit. Failed tests or builds prevent release creation. It uses GitHub's built-in token; no extra secret is needed.

## Workflow

- Add a project using an existing absolute folder path.
- **Future:** parked indefinitely. Messages are saved without starting Codex.
- **Todo:** automatically enters the FIFO queue. By default, only one task runs at a time across all projects.
- **Now:** the worker owns this state. Open the task to read progress, commands, file changes, and replies. Stop moves it back to Future.
- **Done:** Codex ended its run. Questions, refusals, blockers, and failed runs appear as red cards with an attention label; they are unfinished. The browser tab reads **QUESTION** while any Done task needs attention, across all projects. Open the card and use **Send answer & continue** (or Ctrl+Enter) to reply and queue the same conversation. Unfinished tasks cannot be approved for cleanup. A follow-up message moves it to Todo and joins the queue for its project in the same Codex thread. **Approve** starts a 30-minute cleanup countdown. **Revive** cancels it and keeps the task in Done; sending feedback or changing its state also cancels cleanup. When the timer expires, 67ai deletes the Codex sessions, task worktree and branch, board task/conversation, and attachments not used by other tasks. The project folder stays. The countdown survives restarts and runs independently of queue pause; overdue cleanup runs on startup. Session deletion requires a Codex version supporting `thread/delete`. If deletion fails, the task stays with an error; approve again to retry.

Drag cards between Future, Todo and Done. Messages sent during a run wait for a follow-up run; they do not interrupt the current turn. Pause queue prevents new runs while allowing active runs to finish. Failed tasks remain red in Done with an error and require a message or Retry before they run again. Elapsed time is cumulative across runs and excludes queue time.

On Windows, 67ai plays one short dog bark when all queued tasks across projects have finished, including required merges and AI reviews. It also barks when a task needs your attention: questions, blockers, refusals, unconfirmed completion, failed runs or reviews, and merge or cleanup errors, even while other tasks keep running. Each new attention event can trigger a bark; unresolved issues do not repeat. It waits for open boards to apply the task state and stays silent while any 67ai tab is focused. Focus updates run independently of board loading; refocusing cancels a pending bark, and delayed reports cannot overwrite newer focus status. Future tasks and already approved tasks do not block it; failed or unfinished tasks do. It plays once when the queue finishes, including when every task was automatically approved, without repeating when you leave the board or restart with an already completed board or existing attention cards. There is no Windows notification popup. The executable plays the embedded sound through the Windows audio API, with no browser audio; its source and CC0 license are recorded in [assets/sounds/README.md](assets/sounds/README.md).

When Codex reports a usage or rate limit, interrupted tasks and AI reviews return to Todo automatically. New tasks and merges wait until the latest exhausted Codex usage window resets, then resume without a browser open. The pause survives server restarts and keeps the task conversation and pending messages. If Codex cannot report a future reset time, 67ai retries after one minute. A manually paused queue stays paused. Limit-interrupted merge recovery is retried automatically.

Paste images or files with Ctrl+V into task instructions or a follow-up message, drag files onto either editor, or use **Attach files** (25 MB per file). Image previews and file chips can be removed before sending. Attachments persist under the data directory and appear in the conversation for download. PNG, JPEG, WebP and GIF images are passed to Codex as image inputs; other files are provided by their saved local paths. Clipboard file support depends on the browser and source application; drag-and-drop and the file picker are also available.

Use Hard, Easy, or Gen to create a task with the corresponding model from Settings. Tasks show a green Easy, purple Hard, or blue Gen badge on the board and in the task header. The chosen difficulty is saved independently of the model. Older tasks show a badge when their model uniquely matches the current Easy or Hard setting. Ctrl+Enter creates an Easy task or sends a follow-up message. The task header menu contains model selection, AGENTS.md, title editing, deletion, and Stop. Approve appears beside the menu for completed tasks.

Open **Shell inspection** from the application menu for a fullscreen, live view of running programs started by task agents, AI reviewers and merge recovery. The list follows the selected project, including programs left open after a task finishes. Expand a program to see its PID, executable path, launch folder, task and agent role. Exited programs disappear automatically; command history and unrelated operating system processes are not shown. Windows job objects track the actual processes. Successful runs retain their programs until they exit or 67ai closes; stopped and failed runs terminate their process trees. Live shell inspection is supported on Windows.

**Gen** researches a project and creates implementation tasks in **Future**. The application menu begins with **Find issues**, **Gen more content**, and **Gen new features**. Find issues and new features open preset research requests; select a project, adjust the instructions, and choose **Start Gen**. **Gen more content** opens saved content plans: define and try one sample before researching more of that direction. New features proposes new capabilities. The ordinary New task form also includes Gen for custom research requests.

**Content plans** save a brief with a creative direction, one sample scope, confirmed systems/evidence, concrete deliverables, integration paths, technical checks, and instructions for trying the result. Use **Explore content** for guided research, choose and save a direction, then define its single sample with the evidence and checks prefilled. You can also enter a new brief directly. **Make a sample** creates exactly one linked Hard task, using normal execution, merge, and project-specific validation rules. Repeated clicks return the same task, including after cleanup. The agent must verify the brief against current files and ask if its scope or systems are unsupported; levels must not be assumed.

The plan shows the sample's actual status and completion report. Queued, running, blocked, failed, pending review, and unmerged work is distinguished from **Ready to try**; dragging a task to Done is insufficient. After trying it, enter short feedback and choose **Revise sample**, **Use this direction**, or **Set aside**. Revision keeps the brief and feedback and reuses the sample conversation; after cleanup it creates one replacement sample task. Approve and AI approve retain their existing task-review/cleanup behavior and never creatively accept a direction. Plans retain the report, direction, and feedback independently of task/session cleanup and survive restart.

Only a ready sample explicitly accepted with **Use this direction** unlocks **Research next bounded batch**. This creates one research-only Gen task grounded in the implemented sample, feedback, current project files, and existing tasks. It saves at most three Hard tasks in **Future**, each instructed to cover at most one comparable content unit with concrete paths and checks. Follow-ups and task cleanup cannot reset that batch limit. Nothing automatically starts those implementation tasks. Setting a direction aside or revising it blocks queued work from that direction; stale in-flight research cannot save proposals. Old-revision tasks remain visible with an explanation, but cannot run. Open the plan from the task panel's **Content plan & sample feedback** button.

Gen uses its own model from Settings with the same full permissions as other runs. Its instructions prohibit implementation, fixes, production content changes, commits, and deployment, including on follow-ups. It can inspect code/assets, use reverse engineering, and run appropriate research checks. This is an agent instruction, not a filesystem sandbox. Gen runs use the existing project folder, never create task worktrees or trigger automatic commits/merges, and wait for other tasks and merges in the same project. Existing local changes are preserved. Other projects can run concurrently when parallelism is enabled.

For ordinary Gen issues and features, after a successful completed research run, 67ai saves the structured proposals as Hard tasks in Future using the current Hard model. Each includes the proposed scope, evidence or rationale, and acceptance criteria, plus its source Gen task. Existing tasks are provided as context to avoid duplicate work; matching titles are skipped. The Gen conversation records created task IDs. Failed, stopped, usage-limited, invalid, or unfinished runs create no tasks. Follow-ups continue research in the same session. Approving or deleting the source leaves generated cards intact. Easy/Hard auto approval settings do not apply to Gen; manual AI approve reviews its research and proposals.

Content planning inspects actual content definitions, mechanics, reusable assets, authoring tools and representative examples. **View content directions / briefs** in the research task shows the inventory with source paths, unknowns, up to three directions and a recommended first step. A supported type with no examples is reported explicitly; missing tooling or mechanics are labeled **FEATURE WORK** prerequisites, not existing content extensions. Inaccessible evidence remains unknown. Research itself creates no cards.

Choose a direction to review and edit its intended player experience, first batch scope, reuse, authoring requirements, prerequisites, constraints, quality checks and individual tasks. **Save direction** persists the chosen brief and opens the bounded sample form. Research proposals stay as reference; no implementation cards are created until **Make a sample**. Saving the same brief twice is rejected. To obtain different options, use **Ask Gen to revise directions** and send a follow-up in the existing conversation; revisions are research only and preserve earlier evidence. You can also attach references when starting or replying.

The application menu's **Content plans** lists research and saved briefs for the selected project (or all projects). These records, evidence and conversation attachments live in `data/67ai.json` independently of the research task and survive restart, deletion and timed task cleanup. Sample and expansion tasks include the saved direction, brief and evidence. Planning uses the existing Gen worker serialization and research-only instructions; as with ordinary Gen, file-write prevention is an agent instruction rather than a filesystem sandbox.

**AI approve**, beside Approve, queues an independent review using the current Hard task model and a fresh Codex session. The reviewer has the same unrestricted execution permissions as implementation tasks. It reads the full conversation, attachments, code and Git changes, runs relevant tests, and exercises the changed program. For UI changes it must interact with the affected flow and inspect the rendered result, following project testing constraints. Reviews report checks and observations rather than relying only on the original agent's claims or lint. Reviewers leave implementation fixes to the original task agent and clean up their own temporary helpers and processes. The reviewer returns an explicit `approve` or `reject` decision with a message; progress commentary cannot replace that decision. `approve` starts the same 30-minute approval countdown. On `reject`, its feedback appears as **AI reviewer** and queues the original task in its existing session and model, just like your message. A new message arriving during review discards the verdict. Failed or invalid reviews never approve; use AI approve to retry.

In **Settings**, select a project and open **Project AI approval**. **AI auto approve easy tasks** and **AI auto approve hard tasks** are separate, saved per project, and off by default. Enabled tasks are reviewed after successful completion and any required merge; fixes are reviewed again after the original agent finishes. Reviews share the worker limit, pause, and stop controls. Difficulty is saved when creating a task and stays independent of later model changes. Older tasks without a saved difficulty can still be reviewed manually.

Tasks can select another task in the same project as a **Blocker** when created or from the task menu. Changing the project clears the blocker selection. Blocked tasks stay queued until their blocker completes successfully and any required merge finishes; approval is not required. Failed runs and unanswered questions do not release dependent tasks. Circular dependencies are rejected. Remove an unfinished task from dependent tasks before deleting it; deleting or cleaning up a completed blocker clears its references.

Set the Hard task model, Easy task model, and Gen task model in Settings. All initially use your Codex configuration model. Unset models use Codex configuration. The chosen model is saved on each new task; you can change it in the task menu. Model suggestions are read from Codex's local `models_cache.json`; enter additional model IDs in Settings. Model availability depends on your account. Settings accepts the native Codex executable path; Windows npm installations are detected automatically.

Settings also includes **Maximum task workers** (default **4**, minimum **1**) and **Parallelism allowed** (default **off**, including existing installations). When enabled, tasks from the same or different projects can run concurrently in separate Git worktrees under `data/worktrees`, each on its own `67ai/<task-id>` branch based on `main`. Project folders must be Git repository roots with a clean `main` branch checked out and a configured Git commit identity. Uncommitted main changes are never included in task worktrees.

When parallelism is enabled, the task creation row includes an execution selector: **parallel-worktree** (default) uses an isolated worktree; **parallel-raw** uses the project folder without creating a worktree or queuing a merge. Raw tasks also support folders without Git. Their saved mode applies to follow-ups. Runs in the project folder wait for other runs and active merges in the same project; other projects can still run concurrently. Gen always uses the project folder.

One additional merge worker processes completed tasks sequentially. It commits any remaining task changes and merges the task branch into `main`. Tasks remain **orange** in Done until merged, including while a merge is in progress or blocked. Conflicts automatically run a fresh Codex session using the Hard task model (or the Codex default if unset) to reconcile both sides in main. The worker verifies resolution and commits the merge automatically. Recovery activity appears in the task conversation without replacing its original Codex session. If resolution fails, the merge is aborted and the card reports the error; **Retry merge** attempts automatic resolution again. Pending merges survive restarts. Pause stops new tasks and merges; disabling parallelism makes subsequent task runs sequential but still drains completed merges. Lowering the limit does not stop already running tasks. Pending merges cannot be approved, deleted, moved, or given follow-up messages. Task worktrees and branches are retained for inspection and follow-ups until the task is deleted or its approval timer expires. Cleanup deletes the task's Codex sessions, worktree (including uncommitted files), and task branch. If cleanup fails, the task is kept so deletion can be retried. Use **Clear unused sessions and worktrees** in the application menu to select a project and delete sessions (including archived history) and linked worktrees with no existing task. Assigned resources and project folders are preserved. Stop running tasks and wait for merges before clearing a project.

In Settings, select a project and choose **Edit or create AGENTS.md** to edit the file in that project's root, even before creating any tasks. The editor is also accessible inside every task. If the file is missing, write your own instructions or load a shared template and click **Create AGENTS.md**. Other ancestor/global instruction files are displayed read-only, including a root AGENTS.override.md when present. Nested subfolders can have additional instructions. Editing is blocked while this project has a running task, and saving detects external edits. Templates only populate the editor when creating a missing file; they are not injected into task prompts. 67ai sends the task title and pending user messages to Codex. Worktree runs also instruct Codex to stay on the task branch and leave merging to 67ai. A structured final-response schema records whether the outcome is completed, a question, blocked, or refused. Only the reply text is shown in the conversation; missing or invalid outcomes remain flagged as completion not confirmed. Existing saved tasks retain their state until their next run.

Use **Settings → Manage templates** to create, rename, edit, duplicate, or delete shared AGENTS.md templates, including the initial templates. Templates are available across projects and persist across restarts. Changing or deleting one does not modify existing project files.

## Local data and execution

Projects, tasks, conversations, templates and settings are stored in `data/67ai.json`, using a temporary file and atomic replacement. Existing installations migrate their previous data file automatically on startup; stop the old server first. Environment overrides now use the `67AI_` prefix. Codex keeps its own thread history in its normal home directory. A file lock prevents two servers from opening the same data directory. Interrupted tasks return to Future on restart rather than silently rerunning; elapsed time is checkpointed every five seconds.

The server binds only to `127.0.0.1` and rejects foreign Host and Origin headers. All task runs, including fresh tasks, resumed tasks, AI reviews, and merge recovery, use `--dangerously-bypass-approvals-and-sandbox`: no Codex sandbox or approval prompts, with access allowed by the Windows account and any enforced administrator policies. Your configured agent features still apply. On Windows, each run is contained in a kill-on-close job. Stopping or failing a run terminates its child processes; successful runs retain running programs until they exit or the server closes. Concurrency is controlled by the parallelism settings.

Environment overrides:

| Variable | Default |
| --- | --- |
| `67AI_PORT` | `3030` |
| `67AI_DATA_DIR` | The working directory's `data` directory |
| `67AI_CODEX` | Detected native executable; used when creating initial settings |

Run checks with `cargo test`, `node --check web/app.js`, and `cargo build; node tests/integration.mjs; node tests/parallelism.mjs; node tests/ai-approval.mjs; node tests/gen.mjs; node tests/content.mjs; node tests/blockers.mjs; node tests/cleanup.mjs`. The integration suite uses an isolated data directory and a deterministic fake Codex executable; it does not call a model. This checkout pins the installed MSVC Rust toolchain on Windows.

The Gen integration suite can also check the rendered UI in headless, muted Microsoft Edge: install Playwright under `tmp/browser` (`npm install --prefix tmp/browser playwright --no-audit --no-fund`), set `PLAYWRIGHT_MODULE` to `tmp/browser/node_modules/playwright/index.mjs`, and run `node tests/gen.mjs; node tests/content.mjs; node tests/blockers.mjs; node tests/parallelism.mjs`. It starts an isolated test server and never calls a model.

Run the cleanup menu and deletion UI checks with `node tests/cleanup-ui.mjs` after installing Playwright under `tmp/browser` (or setting `PLAYWRIGHT_MODULE`).

Run the shell inspection lifecycle and headless desktop/mobile UI checks with `node tests/shell.mjs` after `cargo build` and installing Playwright under `tmp/browser` as described above.
